Recommendations and Data Security

This chapter walks you through rebuilding the recommendation part of shop-ai: generating data and evaluating the models locally, running the nightly recommendation pipeline on AWS, checking that user data is anonymized, and running a recommendation poisoning experiment. Finish 5.1 Introduction, 5.2 Prerequisite and 5.3 Infrastructure first: the sandbox stack shop-sbx-<name> must be deployed to your account. In this chapter <name> is the name you used in -c owner=<name> when deploying.

Objectives

After this chapter you will:

  • Understand why the team built its own recommendation models on Lambda + DynamoDB instead of Amazon Personalize (ADR-0016).
  • Run two recommendation models locally and compare them with a bestseller baseline using precision@10 and coverage.
  • Run the nightly recommendation job on AWS manually, read its log, inspect the recs table and call the recommendation API.
  • Confirm that the events table holds no real user IDs (HMAC).
  • Measure the impact of fake accounts spamming events, before and after the defenses.

5.5.1. Recommendation architecture

Figure 00. Recommendation diagram with numbered flows 1–6: (1) the web calls the API through CloudFront; (2) VIEW, ADD_TO_CART events are stored with the user id hashed by the HMAC key from SSM; (3) PURCHASE events come from SNS order-confirmed (chapter 5.4) through SQS; (4) at 02:00 every night EventBridge Scheduler runs recs-pipeline, which reads events and products, writes a new version to recs and activates it only when it beats the baseline; (5) the recs Lambda serves the ACTIVE version; (6) CloudWatch alarms when the job has not succeeded (prod). Open the interactive diagram, drawn with the AWSketch skill from a JSON spec. This part is also steps 10–11 of the shared architecture diagram in 5.1.

Recommendation typeMethodData used
Frequently bought togetherAssociation rules (support, confidence, lift) from ordersPURCHASE only
For youItem-based collaborative filtering, cosine similarityVIEW (1), ADD_TO_CART (3), PURCHASE (5); each user–product pair takes the highest weight
Bestsellers (baseline, new users)Count orders over 30 days, fall back to 90 then 365 days if too few, then newest productsPURCHASE

Each night the pipeline writes a new version to the recs table, and only then switches the ACTIVE pointer. Re-running on the same day does not duplicate data; a version that scores worse than the baseline on the last 30 days is not activated.

5.5.2. Preparation

  • Completed 5.2 Prerequisite: AWS CLI, Node, pnpm, the shop-ai repo cloned, the HMAC key /shop/sbx/events/hmac-key created (the key step is in 5.2; without it purchase events fail with ParameterNotFound and go to the DLQ).
  • Completed 5.3: the shop-sbx-<name> stack is deployed.
  • Python 3.13 or later and uv (uv installs the right version from data/.python-version; Python 3.14 is only the Lambda runtime).
  • An account registered on your web app (URL in the WebUrl output of the web stack).
cd shop-ai/data
uv sync
uv run pytest        # environment check, everything must pass

5.5.3. Generate data and evaluate models locally

Generate synthetic data

The generator creates 600 users in 4 groups (gamers, office workers, programming students, designers), buying by built-in patterns (e.g. graphics cards are often bought with power supplies), spread over 365 days, on the web app’s 102 products on sale (the seed in 5.3 loads 104 products; the 2 discontinued ones are left out of the data).

uv run data --out generated --seed 42

The folder has 7 files: users.csv, products.csv, orders.csv, order_items.csv, cart_items.csv, interactions_train.csv, interactions_test.csv.

Evaluate

Train and test sets are split by time (the last 30 days are the test set), the same way the pipeline scores a new version before activating it.

uv run data-eval --data generated            # Frequently bought together vs baseline
uv run data-eval-for-you --data generated    # For you vs baseline

Results over 4 seeds (details in docs/business/recommendation.md section 4.1):

Baseline precision@10Model precision@10Baseline coverageModel coverage

5.5.4. Run the recommendation pipeline on AWS

The pipeline is deployed with the API stack (infra/lib/recs-pipeline.ts): a Python 3.14 Lambda that runs at 02:00 Vietnam time through EventBridge Scheduler, retrying twice on failure. In sandbox, dev and staging the job mixes in synthetic data because there are almost no real buyers; prod uses only real events (SYNTHETIC=0).

Check the schedule

  1. Console → EventBridge → Schedules, open the ...RecsPipelineNightly... schedule of stack shop-sbx-<name>-api.
  2. Check the expression cron(0 2 * * ? *), time zone Asia/Ho_Chi_Minh, target Lambda ...RecsPipeline..., 2 retries.

Run it manually once

  1. Console → Lambda, open function shop-sbx-<name>-api-RecsPipeline....
  2. Test tab → Create new event, name manual, content {} → Test.
  3. Expected result: green “succeeded” box, about 4 seconds, about 100 MB of memory used.

Read the log

Each run prints exactly one JSON line, with counts and scores only, no user IDs. Open the Monitor tab → View CloudWatch logs, or use Logs Insights:

fields @timestamp, products, realEvents, syntheticEvents, gates.ALSO_BOUGHT.model.precision, gates.ALSO_BOUGHT.baseline.precision
| filter message = "Job gợi ý mỗi đêm xong"
| sort @timestamp desc
| limit 5

(The log message is in Vietnamese in the code; keep the filter as is.)

Expected: gates only has ALSO_BOUGHT and FOR_YOU, each with a model score above the baseline. BESTSELLER is the baseline itself, so it has no gate and is always activated. results shows activated: true for ALSO_BOUGHT and BESTSELLER. FOR_YOU is only written for real users (with a userIdHash in the events table), so it may write 0 rows if you have not done the anonymization step below yet. Do that step, then run the job manually again to see rows for FOR_YOU.

Inspect the recs table and call the API

  1. Console → DynamoDB → the ...Recs... table of stack shop-sbx-<name>-api → Explore items, find pk = META: there are 3 pointers ACTIVE#ALSO_BOUGHT, ACTIVE#FOR_YOU, ACTIVE#BESTSELLER, each with activeVersion set to the run date.
  2. In a browser: <WebUrl>/api/v1/recs/bestsellers?limit=3. Expected: "source":"BESTSELLER" and 3 products.
  3. Open a laptop’s detail page on your web app: the “Frequently bought together” block shows a laptop sleeve, a mouse and an HDMI cable.

Alert when the job stops running (prod)

Prod has an alarm recs-pipeline-no-success: it fires when there is no successful run for 26 hours in a row (hours with no data count as failures, to also catch the case where the schedule does not invoke the Lambda). On the first deploy the alarm fires right away because there has been no run yet; one manual run brings it back to OK. How to handle it is in docs/runbooks/recs-pipeline.md.

5.5.5. Anonymizing user data

The events table is the model’s input data. It does not store real user IDs: the events Lambda takes userId from the JWT (it does not trust data sent by the client) and stores userIdHash = HMAC-SHA256(key, userId). The HMAC key is in SSM Parameter Store as a SecureString (/shop/<env>/events/hmac-key, created in 5.2), not in the repo or the template. So anyone who can read the events table or the training data files still cannot tell who an event belongs to.

  1. Sign in to your web app, open a product detail page, click Add to cart (the button label is in Vietnamese on the site: Thêm vào giỏ). Note the time.
  2. Console → DynamoDB → the ...Events... table of stack shop-sbx-<name>-api → Explore items, sort by time.
  3. Check the two new rows VIEW and ADD_TO_CART: userIdHash is a 64-character hex string, with no email or original userId; there is a ttl of 90 days.
  4. Try sending an event while signed out, or sending PURCHASE from the client: the API returns 401 and 400. PURCHASE is written only by the system once an order is confirmed (SNS order-confirmed → SQS → Lambda), exactly once per product in the order.

5.5.6. Recommendation poisoning experiment

An attacker creates many fake accounts and spams views and add-to-carts for a rarely bought product to push it into real users’ recommendations. The experiment runs on synthetic data and computes recommendations exactly as the pipeline does.

cd shop-ai/data
uv run data-poison --seed 42

How events of one user–product pair are combined50 accounts × 50 repeats: % of real users who see the target product
sum: add up every action (the common approach)38.8%–43.2%
max: take the highest weight (what the pipeline uses)0.3%–2.0% (no attack: 0%–3.3%)

Three layers of defense:

  1. Combine with max: repeating an action does not raise the score, so repeated spam has no effect.
  2. “Frequently bought together” learns only from real PURCHASE events: the client cannot send PURCHASE, so this type is not affected.
  3. WAF in prod: a limit of 300 /api/v1/events requests per 5 minutes per IP, plus IP reputation and the core rule set (infra/lib/waf-stack.ts, details in 5.3). The sandbox has no WAF, so this layer can only be checked on the team’s prod.

Known limitation: calling the API Gateway URL directly (bypassing CloudFront) skips WAF; API Gateway throttling and the max layer still apply (threat model C1).

Comparison: Amazon Personalize charges per training hour and per recommendation request, which can cause bill shock during demos; this is why the mentor suggested building our own (ADR-0016).

5.5.8. Clean up

The recommendation part lives only in the API stack (shop-sbx-<name>-api): the pipeline Lambda, the EventBridge schedule, the events and recs tables and the log groups are all deleted with the stack in the sandbox, so follow 5.7 Clean up with no extra step. The HMAC key /shop/sbx/events/hmac-key belongs to no stack; delete it as in 5.7.3, and check Billing the next day as in 5.7.

Note for the team’s prod environment (not needed for the lab): the prod events and recs tables are retained when the stack is deleted (RETAIN), and events also has deletion protection; prod WAF (about $10/month) is cleaned up following docs/runbooks/waf.md, section “Dọn sau khi nộp bài” (cleanup after submission).
