Task details:

Monday (19/10/2026)

  • Cut release/v0.1.0 from develop: 3 days later than planned; sent the team new dates: acceptance 19–21/10, tag 22/10.
  • First staging deploy succeeded: shop-stg-api and shop-stg-web stacks including alarms and dashboard; 104 demo products; smoke tests read the URL from the outputs.
  • Staging E2E user: created in the staging user pool; set the staging environment variables and secret on GitHub; fixed a password mix-up caused by pasting several commands at once with a single command that generates a random password.
  • Re-ran the staging deploy: smoke 6/6, API E2E 4/4 files passed; sent the staging URL to the team for acceptance testing.
  • Reviewed and merged into develop after the release was cut:
    • 3 Dependabot PRs (17 npm minor updates, 2 Python tooling updates).
    • Nhân’s events route contract PR.
    • Checked the Python lockfile still matched; both dev deploys green, smoke 6/6, E2E 4/4.

Tuesday (20/10/2026)

  • Self-study on AWS Skill Builder: started AWS Cloud Quest: Cloud Practitioner, a role-playing game course where each assignment solves a problem in a virtual city with AWS services, with hands-on labs in a real AWS environment provided by Skill Builder; follows the completed Cloud Practitioner Essentials course.

Wednesday (21/10/2026)

  • Team progress on the acceptance deadline: reviewed it; asked the team for results and for Sprint 2 status.
  • Nhân’s OIDC security review issue (#180): verified 5 GitHub safeguards, 4 in place; found the production environment still lets admins bypass approval.
  • Nhân’s synthetic dataset:
    • Ran the generator and offline evaluation.
    • Found the default catalog’s product IDs do not match the shop (0/104).
    • Re-ran with the real catalog (102/102): association rules still beat the baseline but by a smaller margin than published.
  • Nhân’s training data bucket PR (#179): ran tests, synthesized dev and prod through cdk-nag; the dev deploy created the bucket, smoke and E2E green; approved.
  • First real alerts from staging: pre sign-up Lambda errors and p95 latency.
    • Read the logs following the runbook: the pre sign-up Lambda was cut off at 3 seconds (128 MB gives too little CPU; cold starts ranged from 55 ms to over 3 s).
    • The latency alarm was a false positive from cold starts under low traffic.
    • Fixed on the release branch: pre sign-up 512 MB, 5-second timeout (PR #182); approved by Hoàng and Nhân, staging redeployed.
    • Checked the logs when Hoàng re-ran step A3: cold start down to 817 ms (previously cut off at 3,000 ms), duplicate usernames rejected correctly.
  • Cart acceptance testing G1–G6 on staging, all passed: guest cart kept after reload, cart merged on sign-in then on to checkout, quantities accumulate, stock limit enforced, edits and removals update the total, same cart in another browser. Turned off admin bypass on the production environment.
  • Consolidated the team’s acceptance results:
    • Nhân found 2 bugs: missing specs table (fixed in #190), cart icon count (moved to v0.2.0).
    • Hoàng passed 5/6 account steps (enabling MFA moved to v0.2.0).
    • Ran the 4 technical checks on staging: CloudFront cache, 401, X-Ray, error logs.
    • Updated the release checklist with the results (PR #196).

Thursday (22/10/2026)

  • HMAC keys that anonymize userId for Nhân’s events module in all 3 environments (dev, staging, prod): SSM Parameter Store SecureString /shop/<env>/events/hmac-key, generated randomly on my machine, never committed or sent in chat. Verified on dev: POST /api/v1/events returned 202 and the events table stored a hashed userIdHash with a TTL.
  • Released v0.1.0:
    • Opened the release/v0.1.0 → main PR (#205); CI failed at commitlint because about 10 old GitHub-generated merge commits were longer than 100 characters.
    • Found the cause, tested the fix locally against all 100 commits, fixed it on the release branch (#207: skip merge commits ending in (#number), normal commits keep the limit); #205 went green, approved by Hoàng, merged into main.
    • Tagged v0.1.0; Hoàng approved the production environment deploy. The first prod deploy succeeded: shop-prd-api and shop-prd-web stacks, smoke tests 6/6, GitHub Release created automatically.
    • Edited the release notes: summary, acceptance results, what is not in this release.
  • Prod alerts: confirmed the prod alert email; drilled the shop-prd-api-5xx alarm with set-alarm-state: received the ALARM email, then OK about 1.5 minutes later.
  • Merged the release branch back into develop (#209): resolved a conflict in api-stack.ts (kept Nhân’s events infrastructure and the pre sign-up fix), infra tests passed, CI green, dev redeployed.
  • Started Sprint 2: the order-confirmed SNS topic and the events module’s SQS queue (PR #211):
    • HTTPS required, SSE-SQS encryption, raw message delivery without the SNS envelope.
    • DLQ after 5 failures, kept for 14 days; queue policy accepting only this topic (threat model E9).
    • 5 tests, dev and prod synthesized through cdk-nag. Dev deploy green; published a test message to the topic, read it back from the queue as the original JSON, then deleted it.
    • Sent the team how to use it: Hoàng publishes from order-processor, Nhân writes the consumer that records PURCHASE.
  • Prepared the recommendations API:
    • Read Nhân’s nightly pipeline core (#202) and the recs table design; sent Nhân 5 questions (who creates the table, when the pipeline runs on dev, how userId is hashed, where bestsellers come from, the columns).
    • Wrote the OpenAPI contract (PR #213): 3 routes /api/v1/recs/also-bought, for-you, bestsellers, split by access because the HTTP API JWT authorizer is attached per route; the web sends the cart’s product IDs to exclude, the server drops out-of-stock items.
    • Checked with openapi-spec-validator; CI failed once on a flaky web test and passed on rerun; waiting for Hoàng’s review.
  • README in two languages for international readers (PR #215, #217):
    • README.md in English, README.vi.md in Vietnamese, with a language switch.
    • Added the prod demo link, a project status table and a “what this project demonstrates” section; corrected lines that described WAF and the recommendation pipeline as done.
    • Changed the repository description to English; switched the badge to the dev deploy status (PR #217).
  • Agreed with Nhân how the two halves of the recommendations fit together:
    • The recs table format, how userId is hashed, bestsellers written ahead per category.
    • Found that the generator stops at 30/09 so the 30-day bestsellers would be empty, and that prod has no orders yet so the widgets would be empty.
    • Agreed a fallback of 30 → 90 → 365 days → newest products; an alarm when the pipeline does not run (prod only, to stay within the 10 free alarms).
  • recs table (PR #221): pk/sk keys, TTL, on-demand, exposed so Nhân’s pipeline can grant itself write access; 5 tests, checked the table on dev.
  • Recommendations API core (PR #224): selection rules (keep the pipeline’s rank, drop out-of-stock, inactive and in-cart products) and 3 use cases for frequently bought together, for you and bestsellers, with fallbacks when data is missing; 12 tests, layer rules checked.

Friday (23/10/2026)

  • Self-study on AWS Skill Builder: continued AWS Cloud Quest: Cloud Practitioner, building solutions in the real AWS environment provided by Skill Builder.

Saturday (24/10/2026)

  • Hoàng’s ordering design questions, settled the approach:
    • Cross-module table access goes into one ADR-0017 revision written by Hoàng: ordering reads products and carts and writes only the stock column; the recommendations API reads products; the recommendations pipeline may Scan products read-only.
    • Removed the admin email from the order-confirmed topic.
    • New alarms only in prod to stay within the 10 free alarms.
    • If sending to SQS fails after the order is written, still return 201 and log plus emit a metric.
  • Ordering PRs Hoàng had merged (#233, #234, #236, #237): reviewed them, they match the decisions; reminded the team to wait for one approval before merging infrastructure and contract PRs.
  • Nhân’s shared userId hash PR (#225): checked that it is in develop, so the recommendations API hashes the same way as the events module.

Sunday (25/10/2026)

  • Finished the recommendations API (PR #241):
    • Adapters for the recs table (version pointer kept 60 seconds in the Lambda, Query up to 20 rows) and the products table (BatchGetItem with retries for unprocessed keys).
    • Handler validating limit 1–10, exclude up to 20 IDs and category.
    • Lambda and 3 routes: also-bought and bestsellers public, for-you requires sign-in; IAM reads only the right tables and the HMAC key.
    • Added a NEWEST source to the contract for when the shop has too few orders to rank bestsellers.
  • Verified locally: unit tests, integration tests against DynamoDB Local in Docker, cdk synth with cdk-nag, layer rules; CI green, approved by Hoàng.
  • Wrong product ID column name: the API read a different column than agreed with Nhân; the PR was merged before the fix landed, so opened a separate fix PR (#246) and asked Nhân to rename the column in the pipeline and write 20 rows per product.
  • Dev deploy green, called the 3 routes on dev: empty list while the pipeline has not run, 400 for bad parameters, 401 for for-you without sign-in.
  • Settled 3 points with Hoàng for the order confirmation worker:
    • Read the customer email with Cognito ListUsers filtered by sub, only the email attribute, never stored or logged.
    • Create the SES sender identity once with the CLI instead of CDK because dev, staging and prod share one account and region.
    • Keep SES in the sandbox in all 3 environments (200 emails/day, 1 email/second); asked Hoàng to handle throttling.
    • Verified the sender address and stored it as a repository secret; updated deploy.yml and deploy-prod.yml to pass the sender to CDK the same way as the alarm email, and renamed the E2E step per ADR-0018 (PR #261); dev deploy green, address masked in logs.
  • Hoàng’s ordering PRs merged before review (#248 order handler and OrderEnqueueFailed alarm, #254 removing the IAM condition that blocked stock updates): reviewed, fine; noted the account now has 12 alarms, about 0.2 USD/month over the free tier as the team accepted.
  • Nhân’s recs format PR (#250): checked that it matches the recommendations API.
